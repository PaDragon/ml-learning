# Учёт задач разработки ПО

**Тема:** Cистема учёта задач разработки ПО для заказчиков  
**База данных:** develop\_issues

## 1. Вводные

Организация разрабатывает программное обеспечение для Заказчиков. Работа ведётся в разных проектах. Структура данных базы схожа с используемой в организации, но заполнена фейк данными.

**Основные сущности БД:**

| Сущность | Количество |
| - | - |
| Организации-заказчики | 3 |
| Проекты | 12 |
| Спринты | 28 |
| Разработчики (backend, frontend, QA, release manager и др.) | 15 |
| Задачи | 1 000+ |
| Назначения исполнителей (`task\_assignments`) | 2900+ |


**Процесс задачи:**

`backlog → in\_discussion → in\_progress → being\_tested → release`

- Задача может иметь метку `high\_priority` на любом этапе (это **label**, не статус).

- При попадании в спринт разработчику назначается срок (`due\_at`), статус → `in\_progress`.

- После разработки задача передаётся QA; у QA срок может быть явным или не задан (тогда действует SLA **3 рабочих дня**).

- У ~30% задач возможен «ping-pong» между разработчиком и QA (1–3 итерации).

- После приёмки QA задача передаётся release manager и переходит в статус `release`.

**Типы задач:** development (~70%) и incident (~30%).


## 2. Проблема

При выполнении задач исполнители **часто не укладываются в индивидуальный SLA** — срок, выданный конкретному разработчику, QA или release manager на момент назначения.

**Последствия для бизнеса:**

1. **Срыв сроков проекта и релизов** — заказчик получает результат позже, снижается доверие.

2. **«Ping-pong» между исполнителями** — задача многократно передаётся dev ↔ QA, растёт время цикла.

3. **Перерасход ресурсов** — лишние story points, часы (`task\_time\_logs`), нагрузка на команду.

По данным части 1: **57%** завершённых назначений нарушают SLA (2 590 назначений, 1 476 нарушений). Проблема **системная и существенная**.


## 3. Гипотеза

**Если заранее выявлять назначения с высоким риском нарушения SLA и принимать превентивные меры** (пересмотр срока, другой исполнитель, эскалация, дополнительное уточнение требований), то:

- доля нарушений SLA снизится;

- сократится ping-pong dev ↔ QA;

- проекты будут чаще укладываться в плановые сроки.

**Проверка гипотезы:** собрать фактические данные из БД, проверить закономерности SQL-запросами (часть 1), затем обучить модель (часть 2).


## 4. Если гипотеза верна — что мы можем вычислять

| Действие | Описание |
| - | - |
| **Предсказывать** | Вероятность нарушения SLA **на момент назначения** исполнителя на задачу |
| **Предотвращать** | При высоком риске — пересмотреть `due\_at`, назначить более опытного исполнителя, уточнить требования до `in\_progress`, усилить контроль QA |
| **Планировать** | Оценивать нагрузку команды и риск срыва спринта до его старта |
| **Анализировать** | Находить факторы, связанные с ping-pong и инцидентами |



## 5. Модель бинарной классификации (основная ML-задача)

**Тип модели:** бинарная классификация.

**Целевая переменная:** `is\_sla\_breached`

| Значение | Смысл |
| - | - |
| `is\_sla\_breached = 1` | исполнитель **нарушил** SLA (завершил позже effective deadline) |
| `is\_sla\_breached = 0` | исполнитель **уложился** в SLA |


**Определение в SQL:**

```
effective\_due\_at = COALESCE(  
    due\_at,  
    add\_business\_days(assigned\_at, 3)   -- для QA без явного срока  
)  
  
is\_sla\_breached = CASE  
    WHEN completed\_at \> effective\_due\_at THEN 1  
    ELSE 0  
END
```

**Уровень оценки:** одна строка = **`task\_assignment`** (одно назначение исполнителя с собственным SLA).

**Вопрос (как у преподавателя с DVD):** на каком уровне делать оценку — **разработчик** или **назначение**?

| Уровень | Роль |
| - | - |
| **`task\_assignment`** | **Основной** — каждое назначение имеет свой срок, роль и исход; целевая переменная определена естественно |
| **`developer`** | Вспомогательный — агрегаты по исполнителю для описательной статистики (у разных разработчиков breach rate от ~29% до ~81%) |

**Кандидаты в признаки (подтверждены SQL в части 1 и доступны в витрине):**

- тип задачи (`incident` / `development`);

- роль исполнителя (`qa`, `backend`, `release\_manager`, …);

- срок SLA (`allowed\_days`);

- опыт и образование разработчика;

- число назначений на задаче (ping-pong);

- время в статусе `in\_discussion`;

- **заказчик** — организация-заказчик (`organization\_id`, `organization\_name`, отрасль `industry`); в H9 отрасль дала умеренный разброс (~4,6 п.п.), но заказчик остаётся категориальным признаком для части 2;

- **проект** — `project\_id`, `code`, `status`, даты проекта (`started\_at`, `planned\_end\_at`); разные проекты могут иметь разный профиль нарушений SLA;

- **тематика проекта** — отдельного поля в схеме нет; использовать `projects.description` и при необходимости `projects.name` (в части 2 — как текстовый признак или извлечённая категория).

**Слабые / не подтверждены в части 1:** `story\_points`, `has\_high\_priority`, отрасль заказчика как единственный предиктор (H9).

**Текстовые (будущее):** `tasks.title`, `tasks.description`, `task\_comments`, `projects.description`.

**Баланс классов:** 43% / 57% (1 114 / 1 476) — в части 2 учитывать несбалансированность (F1, stratified split).


## 6. Варианты бизнес-задач (альтернативы основной)

Помимо прогноза нарушения SLA, на тех же данных можно ставить другие ML-задачи:

### 6.1. Маршрутизация задачи в нужную роль

**Цель:** автоматически рекомендовать роль исполнителя (backend / frontend / QA / design) при создании или переводе задачи в работу.

|  |  |
| - | - |
| **Тип** | Многоклассовая классификация |
| **Целевая переменная** | `developer\_role\_id` |
| **Признаки** | тип задачи, story points, проект, метки, описание |
| **Бизнес-эффект** | меньше ошибочных назначений, быстрее попадание задачи к нужному специалисту |


### 6.2. Прогноз длительности выполнения

**Цель:** оценить, сколько часов/дней займёт выполнение назначения, чтобы точнее планировать спринт.

|  |  |
| - | - |
| **Тип** | Регрессия |
| **Целевая переменная** | `hours\_to\_complete` (или `days\_to\_complete`) |
| **Признаки** | story points, тип задачи, роль, опыт исполнителя, число передач |
| **Бизнес-эффект** | реалистичные сроки в спринте, меньше систематического занижения `due\_at` |


### 6.3. Прогноз «ping-pong» (передачи задачи)

**Цель:** предсказать, что задача будет многократно передаваться между dev и QA (2+ итераций).

|  |  |
| - | - |
| **Тип** | Бинарная классификация |
| **Целевая переменная** | `will\_reassign` (1 = 4+ назначений на задаче) |
| **Признаки** | тип задачи, story points, время в `in\_discussion`, `high\_priority`, incident |
| **Бизнес-эффект** | раннее уточнение требований, снижение цикла dev ↔ QA |

## 8. Краткий вывод

1. **Ситуация:** компания ведёт разработку для заказчиков через проекты, спринты и цепочки назначений исполнителей.

2. **Проблема:** более половины назначений нарушают SLA → срывы релизов и ping-pong.

3. **Гипотеза:** риск нарушения SLA можно предсказать по метаданным задачи и исполнителя и снизить превентивными мерами.

4. **Основная ML-задача:** бинарная классификация `is\_sla\_breached` на уровне **`task\_assignment`**.

5. **Альтернативы:** маршрутизация по роли, регрессия длительности, прогноз ping-pong.
